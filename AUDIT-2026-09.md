## 3. New findings

Severity scale as before: S1 wrong behaviour reported as success; S2
surprising-but-reported; S3 docs/hygiene/perf. **No S0/S1 findings this
pass.** The list is short and mostly S3 — the two live bugs this branch's
restructuring itself uncovered (variant `skip_if_none`/leniency; the
`char` scratch overflow) were found and fixed before this audit began.

### F1 — S2 — The documented `MAX_DEPTH` default is inert; `Parser::new`/`Lexer::new` do not compile without an annotation

`Parser` and `Lexer` declare `const MAX_DEPTH: usize = DEFAULT_MAX_DEPTH`
on the struct, and the docs say "The default is
[`DEFAULT_MAX_DEPTH`]". But the constructor lives in
`impl<'input, const MAX_DEPTH: usize> Parser<'input, MAX_DEPTH>`, and a
const-generic default on the struct does not flow through a generic
impl block. So the canonical first use — the shape in the README — does
not compile:

```rust
let mut p = json_bourne::Parser::new(b"1 2");
// error[E0284]: type annotations needed for `Parser<'_, _>`
```

Every in-repo call site works around this with an explicit annotation
(`Parser<'_>`, `Parser::<8>`, `Lexer<'_, 8>`) — which means the
annotation-free form is compile-tested nowhere, and a newcomer hits it
immediately. The default is also doing double duty as the "big stack
inline in the struct" knob, so an accidental `Parser<'_, 100000>` is a
100 000-frame stack embed with no diagnostic nudging toward the default.

Recommended action (pick one, ~1 h):
- add `impl Parser<'_, DEFAULT_MAX_DEPTH> { pub const fn new_default(...) }`
  (same for `Lexer`) and update the README's opening example to it; or
- exploit the trick that a non-generic `impl Parser<'_, 128>` block
  *does* see the struct default: `impl<'input> Parser<'input> { pub fn
  new(input: ...) -> Self }` compiles today and makes the annotation-free
  call work exactly as documented; or
- accept the annotation requirement and rewrite every doc claim of "the
  default" to say annotations are mandatory.

The second option is the only one that makes the existing docs true as
written.

### F2 — S3 — `crates/bourne/src/lib.rs` still carries ~1 280 lines of inline public-API tests

The §6 test split moved the nine internals-reachable modules to
`src/tests/` (correctly — those need crate visibility), but the large
`mod tests` block of public-API tests stayed. The file is 1 463 lines of
which roughly 1 280 are that block; the "public surface readable in one
screen" goal of the original finding is met for the *exports*, not yet
for the file. These tests use only the public API, so they can move to
`tests/` with no visibility loss (and gain out-of-crate pinning, the
same argument the previous audit made for `ser_roundtrip`).

Recommended action: one mechanical commit moving the block to
`tests/api_smoke.rs` (or split by area), verifying the count is
unchanged before/after. Half a day.

### F3 — S3 — `benches/bourne-bench/benches/floats.rs` module doc is stale

It frames the bench as deciding "whether porting ryu inline is worth ~600
lines" — a decision that was since made and executed (the teju port,
`float.rs` + `teju_gen.rs` + `teju_tables.txt`). The three-way framing
(`bourne_write` / `ryu_direct` / `serde_json`) no longer matches what
the groups measure. Anyone reading the bench to interpret §4.2 numbers
is misdirected at the door.

Recommended action: rewrite the docstring to describe the current groups
(teju variants vs `serde_json` vs direct `ryu`); 15 minutes.

### F4 — S3 — `.cargo-crap.toml` is tracked but nothing runs `cargo-crap`

The config is thoughtful (threshold 21, pessimistic missing-coverage,
documented exclusions) — which makes its presence as dead weight more
misleading, not less. It appears in neither `scripts/ci.sh` nor
`ci.yml`, and the tool is not a dependency of anything in the repo.

Recommended action: either add a `crap` recipe to `ci.sh` (a coverage
run feeding cargo-crap; add to the `all` case) or delete the file. An
audit-style document referencing a quality gate that never executes is
worse than not having one.

### F5 — S3 — Property-test gaps: no string round-trip, no wide-int, no map properties

`tests/properties.rs` covers i64/u64/f64 round-trips (the f64 property
correctly goes through bourne's *own* serializer, good), never-panic,
error-position bounds, and synthesized-JSON parse. Missing:

1. **String round-trip** — for arbitrary `&str` including escapes,
   control chars, surrogates encoded as pairs, and non-BMP scalars:
   `to_string(&s)` must parse back to `s` bit-exact. Escape handling is
   exactly where the last two live bugs lived (variant `skip_if_none`,
   `char` scratch overflow); a property here would have caught both.
2. **Wide integers** — `i128`/`u128` round-trip properties (the
   exhaustive-ish table tests exist for i64/u64 paths only).
3. **Map duplicate keys** — `BTreeMap`/`HashMap` from docs with
   duplicate keys must error (currently only fixed-case tested).

Recommended action: three `proptest!` blocks, an afternoon including
shrink-tuning for the string generator.

### F6 — S3 — Fuzz targets do not exercise `skip_value` / `Checkpoint` restore

`AUDIT.md` §3.15 asked for `skip_value` and `Checkpoint` coverage in the
fuzz targets; the new `derived` target covers the derive surface (good)
but `stream` still only walks `next_event` and `typed` only parses
concrete types. The skip path is the code with the most delicate
cursor/bookkeeping invariants (and the one that changed for §3.7).

Recommended action: extend the `stream` target to, per input: drive
`next_event` to completion; then `Lexer::try_new` + `skip_value` walk;
then a checkpoint/restore loop interleaved with events. An hour of
target code, and it retires the last open item of the old §3.15 list.

### F7 — S3 — Two CI steps cannot be reproduced in this environment

Bare-metal `no_std` cross-builds and the fuzz smoke need target/toolchain
pieces absent locally. Not a code finding; it bounds what this audit can
assert. If reproducibility off-CI is desired: `rustup target add` for
the two bare-metal triples and a `musl-g++`-providing package for the
fuzz smoke would close the gap in `scripts/ci.sh`'s story.

## 4. Performance

Method note: divan at 25 samples (`DIVAN_SAMPLE_COUNT=25`), single run,
no warm-up discipline beyond divan's default — treat as orientation
against the §4 numbers, which were measured with more care. Absolute
throughputs are labelled; ratios are the meaningful part.

### 4.1 Parse side — bourne leads on every workload

| workload (10 000 elems unless noted) | bourne | serde_json | ratio |
|---|---|---|---|
| stream ints → events | 214.6 µs (233.8 MB/s) | 891.1 µs (DOM) | 4.2× |
| stream strings → events | 241.1 µs (684.6 MB/s) | 711.5 µs (DOM) | 3.0× |
| `Vec<i64>` typed | 72.6 µs (678 MB/s) | 97.8 µs | 1.35× |
| `Vec<&str>` typed (borrowed) | 119.9 µs (**1.39 GB/s**) | 208.1 µs | 1.74× |
| `Vec<String>` typed | 410.2 µs | 545.9 µs | 1.33× |
| typed struct (`metric_events_1000`) | 170.6 µs (858 MB/s) | 300.2 µs | 1.76× |
| small object typed | 135.7 ns | 230.7 ns | 1.70× |

The §4 headline ("typed_struct is the headline number") holds and
improved: serde gap widened from ~1.4× to ~1.8× on the realistic struct.

### 4.2 The derive now beats the hand-written impl

| `metric_events_1000` | median |
|---|---|
| hand-written impl | 170.6 µs |
| **derived** | **162.5 µs (0.95×)** |
| derived, `_lex` key path | 182.7 µs |
| derived, reversed key order | 162.6 µs |

The old audit's target ("derived ≤ 1.05× hand-written") is beaten: the
derive is 4–5% *faster* than the hand-tuned bench impl, in both key
orders, and the `_lex` fallback path costs only ~7%. `small_bourne` vs
`small_bourne_derived` is a tie within noise. Item 16 of the old plan is
done and over-delivered; no action remains.

### 4.3 Float serialization — the §4.2 regression is closed

| `Vec<f64>` n | bourne teju | serde_json | note |
|---|---|---|---|
| 100 | 2.086 µs (48 M item/s) | 2.509 µs | bourne ahead |
| 1 000 | 21.21 µs (47 M item/s) | 23.95 µs | bourne ahead |
| 10 000 (mixed magnitudes) | 260.9 µs (38 M item/s) | 238.6 µs | serde ahead ~9% |
| 10 000 (same-value variant) | 229.6 µs (43.5 M item/s) | 234.5 µs | parity |

The old finding — 10.5% behind at n=10 000 with an 8.4× branch-miss
excess — is now: mixed-magnitude arrays ~9% behind (vs 10.5% then),
uniform-value arrays at parity, and bourne *ahead* at n ≤ 1 000 where
reservation and setup amortize better. The branch-misprediction
attribution in the old §4.2 remains the right lever if anyone wants the
last 9%; it is a worthwhile optimization only if mixed-magnitude
float-array writes are actually your hot path. Recommendation: no
scheduled work; keep the diagnosis attached to the bench.

### 4.4 Performance recommendations

1. Nothing scheduled. The old plan's perf items are either landed
   (escape scan, float fast path, bitset stack, windowed reservation,
   derive dispatch) or measured-and-rejected with the fixtures kept
   (SIMD whitespace, SWAR digits, pair-LUT) — the rejections were the
   right calls and should not be retried without a new insight.
2. If float-array writes ever become a fire: target the shape-selection
   branches in `write_f64_to_ptr` (see old §4.2 note), and re-run
   `--bench floats` with full samples before/after.
